# Telegram Web Proxy Installer by xanka

Автоматический установщик **Telegram WEB Proxy**. Трафик Telegram идёт внутри обычного
HTTPS/WebSocket на порт `443`, поэтому выглядит как посещение обычного сайта и переживает
блокировки, которые ломают классический MTProto-прокси.

Скрипт разворачивает официальный стек проекта
[`telegramdesktop/tproxy-server`](https://github.com/telegramdesktop/tproxy-server):

```text
Интернет :80/:443 -> Caddy -> 127.0.0.1:8080 tproxy-server -> 127.0.0.1:2398 MTProxy
```

Наружу слушает только Caddy. Порты MTProxy (`2398`, `8888`) и релея (`8080`, `8081`)
закрываются правилом nftables.

## Требования

- **x86_64** сервер (официальное ядро MTProxy собирается только под x86_64 — ARM не подойдёт);
- **Ubuntu 22.04+** или **Debian 12+**, systemd, root-доступ;
- домен или поддомен, A-запись которого указывает на IP сервера;
- открытые входящие TCP **80** и **443**, свободные от nginx/apache;
- ~15 минут (собирается MTProxy на C и релей на Go).

## Установка

```bash
bash <(curl -sL https://raw.githubusercontent.com/kiineld/webproxy/main/install.sh) proxy.example.com
```

Секрет генерируется автоматически. Скрипт **идемпотентен**: если что-то упало, просто
запустите его ещё раз — он продолжит с того же места и переиспользует уже выданный секрет.

### Опции

| Опция | Назначение |
|---|---|
| `--email EMAIL` | контакт для Let's Encrypt (по умолчанию `admin@<домен>`) |
| `--secret HEX` | свой секрет, 32 hex-символа |
| `--site-dir DIR` | ваш собственный сайт-заглушка (нужен `index.html`) |
| `--force-site` | перегенерировать заглушку поверх уже установленной |
| `--site-upstream URL` | проксировать локальное приложение, напр. `http://127.0.0.1:3000` |
| `--static-routes exact\|legacy` | `exact` — только точные имена (`/about.html`), `legacy` — ещё и `/about`; по умолчанию определяется по ссылкам сайта |
| `--base-path SLUG\|none` | путь, под которым живёт прокси; `none` — корень домена. По умолчанию новая установка получает случайный путь, повторная сохраняет прежний |
| `--ad-tag HEX\|none` | рекламный тег от [@MTProxybot](https://t.me/MTProxybot); `none` — отключить. По умолчанию — прежний выбор или тег автора скрипта (см. ниже) |
| `--workers N` | воркеров MTProxy (по умолчанию 1) |
| `--max-connections N` | соединений на воркер (по умолчанию 4096) |

## Подключение

После установки данные лежат в `/root/telegram_webproxy_info.txt`. **Берите значения
оттуда, а не собирайте вручную**: по умолчанию прокси работает под случайным путём
(base path), и тогда и адрес, и секрет для клиента отличаются от домена и hex-секрета.
В клиенте Telegram выберите тип прокси **WEB** и введите два значения:

```text
Proxy server: proxy.example.com/phcf2vfe7zgbrslg
Proxy secret: cIVhlEBk_HMMv6RHNWLY7Fk
```

Ссылка: `https://t.me/webproxy?server=proxy.example.com%2Fphcf2vfe7zgbrslg&secret=cIVhlEBk_HMMv6RHNWLY7Fk`
(`t.me` этот маршрут пока не публикует, ссылку нужно открывать прямо в клиенте;
эквивалентная форма — `tg://webproxy?...`).

Под base path клиентский секрет — это base64url от байта `0x70` и настоящего секрета
(так требует апстрим, см. [BASE_PATH.md](https://github.com/telegramdesktop/tproxy-server/blob/main/BASE_PATH.md)).
Внутренний hex-секрет MTProxy в info-файле указан отдельно: он нужен для @MTProxybot,
а в клиент его вводить нельзя. С установкой `--base-path none` прокси живёт в корне
домена, и тогда `Proxy server` — просто домен, а `Proxy secret` — тот же hex.

WEB-прокси поддерживают Telegram Desktop и экспериментальные сборки Android/iOS —
это proof-of-concept, обычный мобильный Telegram из стора его пока не умеет.

## Рекламный тег

MTProxy умеет показывать подключившимся спонсорский канал. Для этого прокси
регистрируется в [@MTProxybot](https://t.me/MTProxybot), бот выдаёт тег (32 hex),
и MTProxy запускается с `-P <тег>`. Для WEB-прокси это работает так же: клиент
по-прежнему говорит с официальным MTProxy, а тот передаёт тег вместе со всеми
запросами в Telegram.

**По умолчанию скрипт ставит тег автора** `2e99d97081ce651f5a42da2ec7bdb004`.
Свой тег или отключение:

```bash
bash install.sh proxy.example.com --ad-tag <ваш_тег>
bash install.sh proxy.example.com --ad-tag none
```

Выбор сохраняется в `/etc/mtproxy/ad-tag.env` и переживает повторные запуски.
Канал для показа задаётся в самом боте. Регистрируя прокси в боте, укажите
`proxy.example.com:443` и **внутренний** hex-секрет из info-файла. Проверить, что тег
применён:

```bash
tr '\0' ' ' < /proc/$(systemctl show -p MainPID --value mtproxy)/cmdline; echo
```

В конце командной строки должно быть `-P <тег>`. Спонсорский канал Telegram
показывает не сразу и не тем, кто уже на него подписан.

## Проверка

```bash
systemctl --no-pager --full status caddy tproxy-firewall mtproxy tproxy-server
```

```bash
curl --fail http://127.0.0.1:8081/readyz
```

Снаружи порты `2398`, `8888`, `8080`, `8081` должны быть недоступны.

## Сайт-заглушка

Если `--site-dir` не задан, генерируется видеоплатформа: лента с живыми эфирами,
сетка роликов, страница просмотра с плеером и главами, каталог, «о проекте»,
приватность и 404. Долгие хронометражи (полевые записи на десять часов, slow TV,
живые эфиры) и текст про лестницу качества 2160p60 объясняют, почему через домен
идёт много трафика.

Палитра, подбор и порядок карточек детерминированно зависят от домена, поэтому две
установки не совпадают побайтово. Разметка соответствует требованиям апстрима:
внешний `styles.css`, никаких инлайновых стилей и скриптов, форм, фреймов и внешних
ресурсов — только `favicon.svg` и своя CSS. Ссылки ведут на точные имена файлов
(`/watch.html`, `/about.html`), как требует режим `static_routes: exact`.

Апстрим больше не превращает `/about` в `/about.html`. Если уже установленный сайт
ссылается на страницы без `.html` (например, заглушка прошлой версии скрипта),
скрипт сам включает `--static-routes legacy`, и ссылки продолжают работать.

Заглушка уже установлена, а хочется сгенерировать заново:

```bash
bash install.sh <домен> --force-site
```

Прежний `/srv/tproxy-site` при этом сохраняется рядом с меткой времени.
Свой настоящий сайт всегда лучше шаблона — положите его в `/srv/tproxy-site`
и перезапустите релей:

```bash
systemctl restart tproxy-server
```

## Если что-то не работает

| Симптом | Причина и что делать |
|---|---|
| `требуется x86_64` | ARM-сервер (Oracle Ampere, Hetzner CAX). Возьмите x86_64. |
| Порт 80/443 занят | `systemctl disable --now nginx` (или apache2). |
| Нет сертификата | A-запись не указывает на сервер, либо 80/443 закрыты фаерволом провайдера. `journalctl -u caddy -n 50` |
| `mtproxy` не стартует | `journalctl -u mtproxy -n 50`; проверьте `/etc/mtproxy/proxy-multi.conf`. |
| `mtproxy`: `status=203/EXEC` | Права на `/opt/MTProxy`; закреплённая версия апстрима чинит их сама при каждом запуске. Крайняя мера: `rm -rf /opt/MTProxy` и повторный запуск. |
| Клиент открывает обычный сайт и не подключается | Неверная пара сервер/секрет. Под base path сервер — `домен/путь`, секрет — base64url-строка из info-файла, а не hex. Используйте ссылку из `/root/telegram_webproxy_info.txt`. |
| Клиент пишет «неподдерживаемый тип прокси» / просит обновиться | Клиент не умеет base path. Обновите клиент или переустановите с `--base-path none` (ссылка сменится). |
| Ссылки сайта отдают 404 | Сайт ссылается на `/about` вместо `/about.html`. Запустите с `--static-routes legacy` или поправьте ссылки. |
| Нет спонсорского канала | Проверьте `-P` в командной строке mtproxy (раздел «Рекламный тег») и канал в @MTProxybot. |
| `tproxy-server did not become ready` | `/readyz` подключается к бэкенду `127.0.0.1:2398`, то есть к MTProxy — смотрите статус `mtproxy`, а не релея. |
| Прокси перестал работать через недели | Конфигурация DC Telegram обновляется таймером `refresh-mtproxy-config.timer` — проверьте `systemctl status refresh-mtproxy-config.timer`. |

## Что было исправлено в этой версии

Скрипт перестал работать после обновлений апстрима (`telegramdesktop/tproxy-server`),
потому что брал его последний коммит, а тот поменял поведение по умолчанию:

1. **Base path по умолчанию.** Новая установка апстрима теперь работает под случайным
   путём (`proxy.example.com/phcf2vfe7zgbrslg/`), а клиенту нужен адрес с этим путём и
   секрет в форме base64url с маркером `0x70`. Скрипт же печатал голый домен и hex-секрет:
   клиент выводил из них capability для корня, релей её не узнавал и отдавал обычный
   сайт — прокси «не работал» без единой ошибки в логах. Теперь адрес, секрет и ссылка
   вычисляются из `/etc/tproxy-server/config.json` ровно так, как это делает апстрим.
2. **`static_routes: exact` по умолчанию.** Заглушка ссылалась на `/watch`, `/about`,
   `/privacy` — все эти ссылки стали отдавать 404. Теперь ссылки ведут на `.html`, а для
   старых сайтов включается `legacy`.
3. **Апстрим закреплён на проверенном коммите** (`c8adb8b`), чтобы такие изменения больше
   не ломали установку молча. Другой коммит: `TPROXY_REF=<коммит|ветка> bash install.sh ...`.
4. Обходные пути для umask (пункт 10 ниже) убраны: апстрим исправил оба бага сам
   (коммиты `51215a2` и `c8adb8b`), его тесты проходят под `umask 077`.
5. После перезапуска релея скрипт ждёт `/readyz`, а секрет с префиксом `dd`
   корректно переиспользуется при повторном запуске.
6. Добавлена поддержка рекламного тега (`--ad-tag`).

### Предыдущая версия

Версия до этой не работала на типовом VPS. Основные причины:

1. **`apt-get install golang`** ставил Go 1.18 (Ubuntu 22.04) или 1.19 (Debian 12), а релею
   нужен Go ≥ 1.20 — сборка падала. Теперь Go 1.26 ставится официальным установщиком
   с проверкой контрольной суммы.
2. **`/var/lib/caddy` оставался root:root** — Caddy не мог записать сертификаты, HTTPS не поднимался.
3. **В `mtproxy.service` не было секции `[Install]`** — `systemctl enable` падал, автозапуск не работал,
   `Restart=` отсутствовал.
4. **`systemctl start ... || true`** глушил все ошибки: скрипт печатал «УСТАНОВКА УСПЕШНО ЗАВЕРШЕНА»,
   даже когда не работало ничего.
5. **Файл `/root/telegram_webproxy_info.txt` писался при любом исходе**, а его наличие блокировало
   повторный запуск — после неудачной установки починить её было нельзя.
6. **nftables-правило устанавливалось, но не включалось** — порты MTProxy `2398` и `8888` торчали наружу.
7. **Отсутствовал таймер обновления** `proxy-multi.conf` — прокси деградировал со временем.
8. **`curl` без `--fail`** мог записать HTML-страницу ошибки вместо бинарника Caddy и сделать её исполняемой.
9. **Не было проверок** архитектуры, DNS, занятости портов и готовности сервисов.
10. **Баг апстрима, `umask 077` в `deploy/install.sh`** ломал установку дважды (теперь
    исправлено в апстриме, обходные пути удалены):
    - `go test ./...` запускается под этим umask, поэтому
      `TestLoadAcceptsSystemdCredentialReadPermissions` создаёт файл `0444`, который
      превращается в `0400`, негативная ветка теста не срабатывает и тест падает
      на полностью исправном сервере;
    - `install-mtproxy.sh` наследует тот же umask, `make` создаёт `objs/bin/` и
      `mtproto-proxy` с режимом `0700`, дерево отдаётся `root:root`, а юнит запускает
      бинарник от пользователя `mtproxy` — отсюда `status=203/EXEC`. Заодно чинятся права
      на уже собранном `/opt/MTProxy`, поскольку пересборку установщик пропускает.
